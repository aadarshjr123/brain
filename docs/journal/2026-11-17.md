# 2026-11-17 — M0 tickets BRAIN-1 to BRAIN-5

**Moved:** BRAIN-1 to BRAIN-5 implemented as five stacked PRs (#17 → #18 → #19 → #20 → #21), all In review. CI green on
the two PRs that carry the workflow. Follow-ups BRAIN-17 (#22, ruleset) and BRAIN-18 (#23, dependency bot) created.

**Decisions:**

- ADR-0008: pin TypeScript 6.0.3. TypeScript 7 is `latest`, but typescript-eslint supports `<6.1`, and type-aware lint is part of our review gate.
- ESLint stays on 9.x: the React plugin inside `eslint-config-next` is not on ESLint 10 yet.
- Stacked PRs instead of one big PR: each ticket reviewable on its own, merged bottom-up.
- Merge commits only (squash off): our commits are Conventional Commits; squashing would replace them with PR titles that are not.
- GitHub Actions pinned to commit SHAs, not tags.
- Internal packages are "just-in-time" (export TS source, no build step).

**Problems hit:**

1. _Two copies of typescript-eslint_ (#24). Next's ESLint preset resolved 8.72.2, ours 8.73.0; ESLint refused to register the plugin twice. Fixed with a pnpm override, not config patching.
2. _Commitlint rejected my own commit._ `subject-case` disallows "ESLint, …" as a subject start. Kept the rule. The hook proved itself on its first run.
3. _Rulesets blocked on a private repo_ (#25). The repo is private; free plan has no rulesets or branch protection there. Ruleset kept as code; BRAIN-17 applies it.
4. _Stacked PRs vs. required checks._ #17 to #19 predate the CI workflow, so they can never report `verify`. The ruleset carries a temporary admin bypass; BRAIN-17 removes it.
5. _shadcn init added an unknown `cn` package._ Checked maintainer and source before keeping it (shadcn's own clsx + tailwind-merge replacement). Moved the `shadcn` CLI to devDependencies; it is only a build-time stylesheet import.
6. _zsh is not bash._ A `for … set -- $p` loop silently did nothing because zsh does not word-split. Used `git ls-remote` instead.

**Learned:**

- Prove every guardrail with a deliberate failure (unchecked index, floating promise, missing alt, bad commit message). A green check that never failed proves nothing.
- Turborepo's strict env mode hides undeclared env vars from tasks. Every build-time env var must be listed in `turbo.json`.
